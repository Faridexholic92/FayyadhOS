# 2.11.1 location and Speedtest recovery — release candidate

Version code 18; version name `2.11.1-location-speed-rc`. This is a source repair on the native-glass work, not a stable/commercial release or a confirmed diagnosis of the user's installed TV.

## Repairs

- An explicit Android-location request now survives the permission dialog, paused Activity and controller recreation. A persisted pending flag prevents a recent old fix or a previous retry gate from silently suppressing the requested detection on resume. Requests remain foreground-only; stale callbacks are ignored; denial, manual mode and OFF clear the relevant pending state. No IP lookup or invented coordinates was introduced.
- Existing weather/location menus remain, with an additional direct **Detect lokasi cuaca** entry in Settings. The sharing/permission explanation is still required.
- Speedtest now aims for an approximately 10-second sample with at least 256 KiB actually received, or the 100 MiB cap if reached first. It no longer requires every slower connection to finish all 100 MiB to produce a result. The 120-second hard deadline, 10 MiB request segments, strict response validation, TLS verification, cancellation and route-change rejection remain.
- Final results show the actual bytes and elapsed time for a shorter sample. The UI does not invent a completed 100 MiB transfer. Deadline errors are distinguished from generic endpoint errors. Completion/cancellation clears the stale task handle before retry is offered.
- Existing Jarvis entry remains; Settings also has **Speedtest · Download**. Previous menu indices and actions are retained.

## Verification

- Two location regression tests were rerun against the original location controller after fixing the test's asynchronous dialog dispatch. Both failed at the expected explicit-request assertion; both pass with the repair.
- Clean `bash build-verified-debug.sh`: PASS. **399 tests: 398 passed, 1 skipped; zero failures/errors.** Lint: **0 errors, 88 warnings**, not suppressed or claimed fixed.
- APK DEX audit: 416 app class definitions; all 13 declared app components present. Input/executable-mode guard and whitespace check pass.
- Added deterministic slow-sample, actual-byte UI, timeout, cancellation and direct-menu tests. Existing segmented response/truncation, denial, paused callback and Jarvis flow checks pass.
- Initial full-run setup failed to retrieve the Android 8 Robolectric dependency because of a JVM TLS initialization failure. The exact Maven Central dependency was cached with its published SHA-512 verified, then the complete clean suite passed. No Android version/test was removed and TLS verification was not disabled.
- A single 10 MiB endpoint check from the build machine returned HTTP 200 and exactly 10,485,760 bytes. This is not evidence of throughput or endpoint access on the user's TV.
- Inspected native-render Speedtest ready-state fixtures at 720p and 1080p. They are simulated views, not TV screenshots or performance certification.

## Signing and publication block

The debug and release signing configuration blocks are unchanged. However, an unchanged configuration is not proof of certificate continuity: the current internal debug build's SHA-256 certificate fingerprint is `8d2ad2ae7fe87adadcdf18c760f115f0b55e69c015637bcc8779d2b425ead2ff`, different from the earlier locally delivered debug build (`378db4b45fcc627abb3c14a1bc631e30f43b7d6d64fec506ebdee9b920c60b02`). Neither fingerprint establishes the certificate installed from a GitHub Actions APK.

**Do not distribute this internal APK as an update.** No production signing key was supplied, recovered, substituted or generated by this repair. No new APK is attached to the handoff. The validation workflow now uploads test/lint reports only; its temporary runner-signed debug APK is not published. Historical artifacts are not retroactively approved.

To publish an update, obtain the established owner-controlled signing process, match the installed certificate, build/sign the release artifact and prove an in-place upgrade preserving data. Physical-TV acceptance of location providers, permissions, D-pad actions, network/error behavior and all existing launcher functions remains required. Provider/device limitations cannot be fixed by inventing a location or bypassing TLS.
